# Project Improvement Status

## Purpose

This file tracks project-level improvements needed to make `rl-infra-design-agents` easier to run and more useful for RL infrastructure and algorithm development.

It is separate from `docs/rlinfrawiki-content-status.md`:

- `rlinfrawiki-content-status.md` tracks Wiki page maturity.
- This file tracks runnable workflows, generated workspace quality, task contracts, review gates, and developer-facing usability.

Update this file whenever an improvement item is completed, re-scoped, blocked, or promoted to a higher priority.

## Status Taxonomy

| status | meaning |
|---|---|
| `done` | Implemented and validated with the listed acceptance check. |
| `in-progress` | Work has started, but acceptance checks are not complete. |
| `todo` | Ready for a future agent to implement. |
| `blocked` | Requires missing input, external environment, or a prior item. |
| `deferred` | Useful, but intentionally postponed. |

For open items, priority reflects the recommended implementation order after the real slime RLCR pilot:

- `P0`: can start the loop in the wrong repository, corrupt or wrongly track loop state, contradict a hard gate, or waste rounds after a known external blocker.
- `P1`: materially affects review reliability or whether rounds make substantive progress, but has a bounded manual recovery.
- `P2`: improves operator experience, broadens content/task coverage, or depends on the P0/P1 controls above.

## Immediate Recommended Sequence

1. Keep `make demo`, `make check`, `make render-example`, and `make review-gate` green after any RLInfraWiki submodule update.
2. Keep `make demo-slime-grpo-contract`, `make demo-rollout-backend-selection`, and `make demo-training-rollout-mismatch-debug` green as the second, third, and fourth golden paths.

4. For real user tasks, use `make prepare-humanize-task`, copy and commit the staged plan into a normal target-repository path, then run `make start-humanize-task TARGET_PLAN=...` and the generated `launch_humanize.sh`.
5. Use `make import-humanize-round` after Humanize loops to bring review results back into `review_rounds/` and `review_issues.jsonl`, then run the review gate with `--require-review`.
6. Implement P0 `IMP-021`: convert unavailable live validation into a structured operator handoff instead of spending rounds until the stagnation circuit breaker fires.
7. Implement P1 `IMP-022`: validate Round 0 AC coverage and make progress/stagnation decisions acceptance-criteria-aware.
8. Implement P1 `IMP-019`: add bounded retry for transient Codex capacity/network failures while preserving per-attempt diagnostics.
9. Publish or install a Humanize runtime containing `humanize-gate-invariants-v1`; use `HUMANIZE_PLUGIN_ROOT=../humanize` for local development until then.
10. Implement P2 `IMP-017`: auto-answer deterministic plan-comprehension questions and leave only genuine operator decisions interactive.
11. Run a second real-task smoke through the IMP-018/020 launcher and record target-root, local-state, Stop-hook, gate verdict, and import evidence.
12. Resume `IMP-016` only after IMP-018 through IMP-022 pass the second real-task smoke; then decide how much of Humanize execution the one-command operator loop should own.
13. Continue P2 `IMP-005` and `IMP-006` content/recipe expansion in parallel when it does not delay the Humanize P0/P1 controls.
14. Watch GitHub Actions after each push; fix submodule, dependency, or review-gate drift before expanding content.
